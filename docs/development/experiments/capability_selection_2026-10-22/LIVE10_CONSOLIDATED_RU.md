# Live10 и PR #138: сводный эксперимент с каталогом capabilities

Дата: 22 октября 2026. Статус: **HOLD / исследование, не включать роутинг в production**.

## Что именно сравнивалось

Восстановленный исторический Live10 из #142: десять исходных midgame-пар, исходный порядок A/B, двадцать точных raw parent rows. Это не starter-подмножество Live20. База текущего нативного контракта — `c2899c79fe990583f4be8001721b6ba2f3a438c9`; экспериментальные селекторы — #138, `c84653cc8af56a7ca3f47c3b9cd6a97000356417`. Проверенные registry/schema/validator/compiler/Author/C# файлы не изменились относительно прежней базы `57c58d5`, поэтому старые ответы можно перепроверить текущим runtime.

«Нативный» ниже означает существующий полный каталог и канонический Author-контракт. Генерации выполнены свежими сабагентами **GPT-6 Luna, high**, как просил пользователь. Это не HTTP-запуск `toolbox live10 --run`: у сабагентов другая служебная обвязка, схема дана для чтения, provider constrained decoding не включён. Нет замеров API billing, hidden reasoning, latency или фактических cache hits. Не выполнялись новые Visual/VFX/image/Repair стадии и игровой smoke каждого предмета. Эти ограничения относятся ко всем сравниваемым arms.

| Вариант | Дополнительная стадия | Подробная документация | Назначение |
|---|---:|---|---|
| Native full | 0 | Все 73 карточки | Базовый Author |
| Groups full + тот же план | 1 | Все 73 | Контроль эффекта плана группового селектора |
| Groups selected | 1 | Выбранные группы + положительные зависимости | Первая реализация #138 |
| Exact full + тот же план | 1 | Все 73 | Контроль эффекта плана точного селектора |
| Exact selected | 1 | Выбранные IDs + положительные зависимости | Вторая реализация #138 |
| Compact full | 0 | Все 73 полные карточки, точные повторы вынесены в словарь | Новая проверка сжатия без потери сведений |

Полные и сокращённые matched пары получают один и тот же selector intent, родителей, общий brief сохранения полезных функций и полную provider JSON-схему. Устранена ошибка прежнего дизайна, где только reduced header дополнительно просил сохранять вторичные функции. Отличие authority sentence теперь лишь объявляет законность index-only IDs. Ни validator, ни compiler, ни runtime admission не сужались. В обязательном выборе подробными остались 7–50 карточек по группам (среднее 31,4) и 3–13 по точным IDs (среднее 9). Во всех arms остаются доступными все 73 IDs; при этом **доступность ID не равна наличию полного объяснения его параметров**.

Compact full — не пересказ и не «индекс вместо документации». Словарь хранит точные повторяющиеся JSON-значения, включая объекты параметров, массивы и строки; ссылки раскрываются рекурсивно. Для всех десяти пакетов доказано побайтовое равенство упорядоченного JSON каталога после восстановления. Полнота информации доказана; одинаковая лёгкость чтения для LLM из этого не следует.

## Неожиданный результат первой стадии и раскрытая поправка протокола

В исходном свободном режиме **20/20 решений** — десять групповых и десять точных — выбрали `fullCatalog=true`. При задании сохранить максимум полезного селекторы предпочли не рисковать документацией. Оба reduced arms фактически получили тот же полный каталог, что matched controls. Размер Author вырос из-за плана; input вместе с селектором вырос на **33,8% / 34,5%** без учёта schema/output/reasoning.

Начавшиеся генерации этого режима сохранены. После обнаружения одинаковых пакетов остановлено назначение новых дубликатов; незапущенные trials не объявляются ошибками модели. Исходные решения, пакеты, первые ответы и протокол v1 не переписаны.

Затем добавлено отдельно обозначенное **условие обязательного выбора документации**: `fullCatalog=false`, цель — минимальный достаточный набор для одного полезного гибрида. Число выбранных IDs/групп не ограничено: можно выбрать даже все; runtime admission по-прежнему полный. Это исследовательское давление на экономию, а не доказательство, что свободный селектор сам поведёт себя так же. Новая серия — по десять первых ответов в шести arms. Поправка сделана после просмотра свободных selections и частичной validation, до forced-selector/forced-Author ответов; исследование нельзя называть целиком неизменным preregistered trial.

Каждый Author — отдельная свежая сессия, один ответ, без validator feedback и Repair. Селекторы — батчи по пять случаев; 40 решений двух условий — восемь независимых selector-сессий, а не 40 независимых сессий. Один агент сохранил пять первых selections в неверную подпапку; восстановлены точные байты с SHA256, без повторной генерации.

## Результаты качества

Всего сохранено **70 новых первых ответов Author**: 60 в завершённом сравнении и десять дополнительных ответов свободного режима. Ещё шесть первоначальных native/compact ответов использованы в основной серии без изменений. Сохранены 40 решений селектора и все 42 ответа прежних серий.

| Вариант | Runtime принят и скомпилирован после штатного ingress | Полностью соответствует provider schema | Полное сохранение оцениваемых source functions |
|---|---:|---:|---:|
| Native full | 9/10 | 8/10 | 6/10 |
| Groups full + plan | 10/10 | 6/10 | 9/10 |
| Groups selected | 7/10 | 7/10 | 4/10 |
| Exact full + plan | 10/10 | 6/10 | 7/10 |
| Exact selected | 10/10 | 8/10 | 8/10 |
| Compact full | 9/10 | 7/10 | 8/10 |

Последний столбец — **производная описательная сводка** слепых reviews, а не новый заранее зарегистрированный endpoint: исключены source/catalogue-blocked эффекты и необязательный придуманный placed light; partial/transformed не считается полным сохранением, RED ответ не считается рабочим. Это не измерение надёжности на больших выборках. Особенно спорна степень допустимой замены исходного управления; в raw review оставлены причины и evidence IDs.

У групп matched пары дали 4 случая полного сохранения в обоих вариантах, 5 только у full+plan и 1 без полного сохранения у обоих. У exact — 7 в обоих, 1 только у reduced, 2 без полного сохранения у обоих. Это позволяет отделить наблюдения о плане от сокращения документации, но при одном независимом ответе на случай не доказывает причинность.

**Уточнение оценивания:** сначала черновая проверка подавала сырой provider JSON прямо в runtime validator. Это неверно для nullable schema transport. Итоговые числа используют ровно production `parse_first_valid_llm_json` → bounded input check → `project_provider_author_item_to_local` → validator/compiler. 13 объектов прошли объявленную nullable projection; четыре raw-файла разобраны штатным parser несмотря на обвязку/хвост. Не применялся синтаксический Repair, не удалялись неизвестные/обязательные null-поля, исходные ответы не менялись. Одна malformed запись по-прежнему отвергнута. Синтетические negative witnesses подтверждают, что обязательные/неизвестные null и null-элементы массивов не скрываются.

В чтении для сабагентов использован базовый `_AUTHOR_SYSTEM`, без environment suffix и добавляемой HTTP-пайплайном `provider_nullable_transport_rule` строки. Provider schema предъявлена полностью и одинаково; это ещё одна причина не переносить частоты форматных ошибок в настоящий schema-constrained запуск.

Оставшиеся пять RED: Native Holy Storm, Groups Rain и Compact Rain — consumer-representability гравитационного ускорения; Groups Queen Spider — отсутствующие условно обязательные `bounceCount`; Groups Crystal — повреждённый JSON. Два matched full+plan controls прошли 10/10, что не равно 10/10 полностью сохранённых функций.

Оценивание разделяет: строгий разбор JSON, штатную runtime validation/compile, соответствие полной provider schema и сохранение функций по графу/параметрам. Schema дана модели, но не исполняется как decoder: ошибки, которые constrained decoding механически предотвратит, нельзя переносить в production как измеренную частоту. Аналогично, валидный JSON не доказывает, что у ребёнка включён damage, placement имеет binding или equipped эффект действует в руках.

Рубрика зафиксирована до чтения ответов Author; независимое ревью получает нейтральные IDs, raw parents и рубрику без arm/selector/агрегатов. Основные и вторичные функции оцениваются отдельно: preserved, partial/transformed, lost, source-blocked, catalogue-blocked, unclear. Неполные исходные данные и невозможные сочетания не превращаются в ошибку селектора. Любое уточнение рубрики/спорная трактовка раскрывается, сырые ответы не исправляются.

- **Compact full:** в Queen Spider потеряна поддерживаемая native sentry registration. Информационно обратимое кодирование не гарантирует, что модель воспользуется каждой полезной карточкой.
- **Source-blocked:** точные Shadowflame/Ichor BuffIDs отсутствуют; неподтверждённые числовые догадки не засчитаны как сохранение. Native minion lifecycle и конфликт самостоятельной ammo-role вынесены в catalogue-blocked, а не в ошибки selector.

Ревью также перепроверено по C#: первоначальную претензию к нулевой скорости exact Crystal сняли — `native_shot` передаёт `velocity.Length()` как rootSpeedOverride. Вертикальное падение из точки над cursor с положительной гравитацией засчитано как overhead attack; наклонная начальная скорость не была требованием. Для одной meteor-атаки исправлена формулировка: это gravity arc от activation_origin, а не straight motion. Статус partial из-за отсутствия верхней точки остался. Эти поправки применены к оценке, без изменения model outputs.

Все 60 ответов вместе используют **29/73 capabilities** (24 у native, 23 groups selected, 23 exact selected, 21 compact; число вызовов не является качеством). Остальные 44 и их параметрические/межсущностные комбинации не получили нового генеративного покрытия. 192 structural-проверки сохраняют доступность каталога, но не заменяют quality trials этих механик.

## Экономика: считать оба прохода

Средние за десять случаев. `o200k_base`, compact JSON; это proxy tokens реконструированного request, а не provider usage или полный фактический контекст сабагента с tool-read обвязкой. Неизменный `response_format` занимает около **21 829** proxy tokens. Для сопоставления со старыми отчётами ниже отдельно приведены payload и message contents + schema. Служебный system — 108 tokens. Реальная тарификация schema зависит от provider; здесь нет утверждения об его биллинге.

| Вариант | Author payload | Selector input | Сумма input без внешней схемы | К native | Сумма message contents + schema + selector | К native |
|---|---:|---:|---:|---:|---:|---:|
| Native full | 43 205 | 0 | 43 205 | — | 65 143 | — |
| Groups selected | 29 717 | 14 571 | 44 288 | +2,5% | 66 226 | +1,7% |
| Exact selected | 25 999 | 14 913 | 40 913 | −5,3% | 62 851 | −3,5% |
| Compact full | 39 534 | 0 | 39 534 | −8,5% | 61 472 | −5,6% |

Только Author уменьшается на 31,2% по группам и 39,8% по точным IDs. Эти проценты **нельзя выдавать за экономию всего craft**. Selector output дополнительно в среднем 137/145 proxy tokens; hidden reasoning, изменения Author output, стоимость Repair и лишняя последовательная задержка не входят в таблицу. Общие Visual/VFX стадии также не входят: относительно полного craft выигрыш будет меньше. У exact холодный input выигрывает всего 2 293 tokens в абсолютном выражении; дополнительные output/reasoning/Repair затраты могут съесть этот запас.

Исходная консервативная `non_drivers` политика проверена отдельно как строгая нижняя граница. Даже пустой выбор оставляет 50 reserved capabilities и ещё одну из dependency closure. Без экспериментального brief средний Author может сократиться максимум с 43 050 до 40 125; selector сам требует 18 443/18 785. Суммарный input минимум **+36,0% / +36,8%**. Реальный непустой выбор этот минимум не улучшит. При равной некешированной цене input эта политика не окупается. Подмена этого вывода размером `selected_only` selector была бы ошибкой: у политик разный discovery packet.

## Cache prefix и различная цена моделей

Native имеет один стабильный developer-сегмент длиной **41 532** proxy tokens; Compact — один длиной **37 861**. В этой серии каждый forced selected набор различается: **10 групповых и 10 точных static sets**. Общий prefix разных наборов — около **8 964 / 8 472** tokens. Это не потолок кеша: повтор точно такого же набора может переиспользовать весь его static segment. Ключ/хеш лишь показывает различие запросов, не измеряет попадания backend cache.

Если полный каталог уже тёплый, экономия от удаления его текста существенно дешевле добавленного холодного selector. Если reduced наборы холодные, а native тёплый, селектор может быть особенно невыгоден. Следующая таблица — **условный расчёт**, cached multiplier = 0,1, без output/reasoning/Repair. Отношение цены selector input к Author input должно быть ниже порога.

| Условия | Groups | Exact |
|---|---:|---:|
| Оба холодные | 0,926 | 1,154 |
| Author static тёплый, selector холодный | 0,088 | 0,112 |
| Оба static тёплые для точных наборов | 0,434 | 0,557 |

То есть небольшой холодный выигрыш exact не означает выигрыш при прогретом полном каталоге. Для настоящего решения нужны usage.cached_tokens, реальные цены двух моделей, output/reasoning и latency на одинаковой production transport-конфигурации. Здесь они не измерены. У селектора пока нет production request builder/cache boundary; его static split в расчёте гипотетический.

## Как это сочетается с прежними отчётами

| Серия | Что было проверено | Результат и граница вывода |
|---|---|---|
| Первая: 4 stress cases, 12 Authors | Консервативный reserve, groups/exact | Author −1,9%/−5,5%, два input прохода +45,9%/+43,0%. Валидны 2/4, 3/4, 4/4. Trap содержит неисполняемое совмещение движения/контроллера; pass rate не доказательство полезности |
| Вторая: 3 cases × 2 repeats × 5 arms, 30 Authors | `selected_only`, matched full+plan controls | Author −19,6%/−32,2%, сумма input +18,8%/+6,9%. Native 6/6 accepted+rubric; groups 5/6, exact 5/6. Малый N, разные header-инструкции и отсутствие schema в модельном вводе ограничивали вывод |
| Третий методологический аудит | Семантика schema, cache/cost, witnesses scorer | В 30 ответах использовалась только 21/73 capabilities. Полная strict schema удаляет descriptions/x-infini annotations, поэтому не заменяет значения единиц и совместные requirements. Найдены false-positive witnesses gravity=0 и общего on_use; исторические итоговые числа не изменились |
| Нынешний Live10 | Реальные точные midgame parents; общий brief; полная schema для чтения; free choice и forced selection; Compact full | Новая серия шире по полезным вторичным функциям, но также не является exhaustive proof всех комбинаций 73 capabilities |

Все **42 старых первых ответа** перепроверены текущим Python validator/compiler: снова **9/12** и **26/30** валидных/скомпилированных. Они сохранены, а не заменены новыми ответами. Разные серии не объединяются в один процент «надёжности»: различались задания, документация, controls и способ предъявления schema.

Разница экономики между прошлой и нынешней сериями объяснима: нынешний динамический контекст в среднем около 1,7k против примерно 5,1k ранее. Селектору тоже приходится читать этот контекст. Чем он тяжелее, тем меньше выгода дополнительного прохода. Здесь проверяется эта зависимость, а не универсальная победа/поражение одной архитектуры.

## Что в каталоге/данных мешает честной оценке

Сохранились шесть прежних findings: controller подавляет движение; `item_body.on_use` общий; prose generated-buff activation не отражает held/event alternative; нет arbitrary held defense; обязательные нейтральные поля имеют условные правила; `live_parent` не включает child damage lane.

Live10 добавил важные границы: native minion lifecycle не предоставлен, хотя sentry registration есть; ammo-consumer и самостоятельная ammo-item роли взаимоисключаются; в dump нет точных on-hit BuffIDs для Shadowflame/Ichor; ingredient identity не наследуется автоматически. Напротив, **все нужные boots/ice/flight/hot-block/knockback/wire функции уже доступны**. CrystalShard — реальный placeable, не просто декоративный ингредиент. Подробности, последствия и доработки — в отдельном [каталоге ограничений](../../CATALOG_LIMITATIONS_RU.md).

## Проверки и воспроизводимость

Пройдены 24 focused теста #138, 85 toolbox tests, 192 проверки вариантов документации, 10 точных roundtrips compact-каталога; повторены шесть старых catalogue witnesses. Новые ответы проверяются без Repair штатным validator/compiler, отдельно provider schema и рубрикой.

На точном дереве, вошедшем через #142 в текущий main, проверен [CI run](https://github.com/Xipong/InfiniCrafterLocal/actions/runs/39795380505): Windows build/package успешен, **383 native CPU checks passed, 0 failed**. ## Решение

1. **Групповой роутинг для экономии не внедрять:** в этой серии он дороже по input и заметно хуже matched full+plan по сохранению функций. Консервативный reserve тоже не окупается при равной холодной цене.
2. **Exact selection не объявлять мёртвым, но оставить HOLD:** здесь он дал 10/10 принятия и 8/10 полного сохранения оцениваемых функций, против 10/10 и 7/10 у собственного full+plan control. Это маленький положительный сигнал, а не доказательство non-inferiority всего каталога. Чистая холодная экономия вместе со схемой всего 3,5%, до output/reasoning/Repair; при тёплом native-prefix может исчезнуть.
3. **Compact full — более прямой кандидат на дальнейшую проверку экономии:** 5,6% input вместе со схемой без дополнительной стадии, все сведения сохранены. Однако пропуск sentry и 9/10 runtime acceptance запрещают объявлять безвредность только по roundtrip proof. Production-код не заменён.
4. **Планирование отдельно от экономии оказалось интересным:** Groups full+plan дал 10/10 принятия и 9/10 полного сохранения против native 9/10 и 6/10, но добавил около 22,5% холодного input вместе со схемой. Если платить ради качества, проверять надо именно этот эффект, с повторениями и настоящим transport, а не приписывать его удалению карточек.

Иллюстрация только на этой выборке: input-proxy на один ответ с полным сохранением функций составляет примерно 109k native, 89k groups full+plan, 166k groups selected, 114k exact full+plan, 79k exact selected и 77k compact. Это простое деление входа на наблюдаемые 6/9/4/7/8/8 успехов; output, hidden reasoning, cache, Repair и статистическая неопределённость отсутствуют. Значит, даже дорогой планировщик потенциально может оправдаться качеством, но **этого исследования недостаточно для обещания реальной денежной экономии**.

**#138 остаётся Draft/HOLD.** В main не включены ни selector, ни compact encoding. Практическая ценность текущего результата — более узкий выбор следующей проверки, воспроизводимые первые ответы и отдельный список конкретных ограничений/ошибок контракта.
